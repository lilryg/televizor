# Аудит трансляции вкладки

## Исходная реализация

Контрольная точка — [ab280d6](https://github.com/lilryg/televizor/tree/ab280d6d11e0b21a9dfd49fcd11d95a4ece29cdf). Хост запрашивал вкладку с её звуком и с максимальными ограничениями 1920×1080 и 30 кадр/с. Chromium мог вернуть меньшие значения. Все дорожки добавлялись в одно соединение с каждым зрителем. Браузер выбирал кодеки, способ кодирования и битрейт. Приложение не задавало битрейт, разрешение отправителя и порядок кодеков.

Зритель получал один MediaStream через `srcObject`. У видео были `autoplay` и `playsInline`. Плеер стартовал без звука, пока зритель не включал его. Буфером управлял браузер. Supabase передавал сигналы SDP и ICE, видеоданные шли по выбранной WebRTC паре. В конфигурации по умолчанию два публичных STUN-сервера, TURN добавляется отдельно через `VITE_ICE_SERVERS`.

При потере сигнализации код мог перекрыть живой поток сообщением о восстановлении. После потери ICE таймер мог заменить соединение до завершения его собственного восстановления. Из кода нельзя установить фактический кодек, аппаратное ускорение, потери или причину регулярных рывков на конкретных устройствах.

## Изменения

- **Стабильный** запрашивает до 1280×720 при 30 кадр/с. **Сбалансированный** по умолчанию запрашивает до 1920×1080 при 30 кадр/с. В обоих режимах Chromium адаптирует битрейт. **Высокое качество** запрашивает до 1920×1080 при 60 кадр/с и задаёт верхнюю границу 10 Мбит/с без нижнего порога и без фиксированного целевого битрейта. Режим выбирается до начала захвата.
- У дорожки захвата выставляется `contentHint = 'motion'`, а отправитель просит при перегрузке сохранять частоту кадров. Масштабирование отправителя оставлено браузеру. Звук передаётся в том же соединении.
- Краткий разрыв ICE даёт браузеру время восстановить соединение. При исчерпании ожидания зритель повторяет попытку. При потере одного лишь канала сигнализации живой медиапоток остаётся видимым.
- Кодек по умолчанию выбирает браузер. Для контролируемого сравнения у обоих участников можно задать `?webrtc=1&rtc-codec=h264` перед `#room=…`. Допустимы `vp8`, `vp9`, `av1`. При отсутствии поддержки сохраняется штатное согласование. Значение в панели берётся из активной записи RTP и связанного отчёта кодека.

## Чтение диагностики

Открой комнату с `?webrtc=1` перед `#room=…`. Во время трансляции панель ниже плеера обновляется раз в секунду. Хост получает отдельный отчёт по каждому соединению. Счётчики показывают разницу между измерениями, битрейт и FPS вычисляются по времени между ними. Если браузер не сообщает метрику, панель показывает «Недоступно». Стандартный отчёт отправителя не предоставляет собственный счётчик отброшенных кодировщиком кадров.

`qualityLimitationReason = cpu` показывает, что браузер ограничивает качество из-за вычислительной нагрузки. `bandwidth` означает ограничение полосы по оценке браузера. Название реализации и флаг энергоэффективности помогают исследовать кодирование, но наличие кодека в списке возможностей само по себе не свидетельствует об аппаратном ускорении. RTT характеризует путь туда и обратно. Оценка от захвата до показа вычисляется отдельно через метаданные кадров, если Chromium их отдаёт. [WebRTC Stats (W3C)](https://www.w3.org/TR/webrtc-stats/)

## Проверка на двух компьютерах

1. Подключи одного зрителя. На обоих компьютерах открой комнату с `?webrtc=1`. В качестве вкладки для захвата открой [тестовый сигнал](https://lilryg.github.io/televizor/webrtc-clock.html) на компьютере хоста. При желании включи звуковые импульсы и передачу звука при захвате.
2. Сравни одинаковые отрезки по 30–60 секунд. Запиши кодеки, разрешение, FPS, битрейт, RTT, потери, отброшенные кадры, время кодирования и декодирования. Сравни нагрузку CPU и GPU на тех же устройствах. Для проверки влияния кодека повтори с одинаковым источником, профилем и сетью и сверь, что диагностика показывает нужный кодек.
3. Для визуальной оценки задержки сними оба экрана одной камерой или сравни время на тестовом сигнале с UTC на синхронизированном компьютере. Звуковой импульс и вспышка шкалы начинаются на границе секунды и помогают заметить рассинхронизацию. Проверь прерывание и восстановление связи зрителя.
4. Для сравнения с исходным вариантом используй контрольную точку на отдельном локальном запуске. В Chrome можно открыть `chrome://webrtc-internals` перед установлением соединения и снять те же RTP и ICE метрики. На компьютере хоста тестовое видео и тестовый сигнал должны быть одинаковыми для обеих версий.

Автоматизированное сравнение через `npm run test:webrtc` устанавливает два настоящих WebRTC-соединения в Chromium на одном компьютере по очереди. Источник — движущееся тестовое изображение 1080p/30 и звуковая дорожка. Первый проход использует исходные настройки, второй — настройки сбалансированного профиля. Тест проверяет получение обеих дорожек, согласованный кодек и отображение кадров. Он не моделирует захват вкладки, сеть между компьютерами или аппаратный кодировщик пользователя.

## Измерения в Chromium

Результаты одного прогона после 12 секунд прогрева. Параметры RTP усреднены по следующим четырём секундам. Задержка измерена по отметке времени, закодированной в самом изображении. [Лог GitHub Actions](https://github.com/lilryg/televizor/actions/runs/44795212333).

| Метрика | Исходный вариант | Сбалансированный |
| --- | ---: | ---: |
| Фактические кодеки | VP8 / Opus | VP8 / Opus |
| Разрешение отправки и приёма | 640×360 | 640×360 |
| Кодирование / декодирование | 29,7 / 29,7 кадр/с | 29,7 / 29,7 кадр/с |
| Видеобитрейт | 1,71 Мбит/с | 1,71 Мбит/с |
| Тип ICE и протокол | host / host, UDP | host / host, UDP |
| RTT | 1,0 мс | 0,0 мс |
| Потери / повторные передачи / пропуски у зрителя | 0 / 0 / 0 | 0 / 0 / 0 |
| Среднее время кодирования / декодирования | 3,5 / 1,3 мс | 3,4 / 1,3 мс |
| Средняя задержка в jitter buffer | 9,1 мс | 10,7 мс |
| Задержка от отметки в кадре до показа, медиана / p95 | 43 / 58 мс | 43 / 55 мс |

В обоих случаях браузер сообщил ограничение `bandwidth` и снизил разрешение относительно тестового источника. Локальный прогон не подтвердил прирост плавности, снижение медианной задержки или достижение Full HD. Для исходной проблемы нужны данные с устройств хоста и зрителя, между которыми видны рывки.
